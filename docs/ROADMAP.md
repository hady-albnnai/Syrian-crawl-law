# خارطة طريق مشروع ميزان
## الزاحف الذكي ومعالجة القانون السوري

**الإصدار:** 1.0
**تاريخ إعداد الخطة:** 2026-09-05
**المستودع:** `Syrian-crawl-law`
**المنتج المستهدف:** ميزان — النظام الذكي للقانون السوري

---

## 1. الغرض من هذه الوثيقة

توحّد هذه الوثيقة الوصف المقدم لمشروع ميزان مع الحالة الفعلية للمستودع الحالي، وتحدد الطريق الآمن لبناء طبقة جمع ومعالجة واسترجاع النصوص القانونية السورية.

الخطة موجهة إلى:

- تطوير الزاحف الحالي دون فقدان ما تم إنجازه.
- تحويل الاستخراج من نموذج تجريبي إلى Pipeline قابل للاختبار والاستئناف.
- تجهيز البيانات للانتقال إلى PostgreSQL و`pgvector`.
- توفير أساس موثوق للبحث الدلالي ثم RAG.
- إبقاء كل إجابة قانونية قابلة للتتبع إلى الوثيقة والمادة والمصدر.

هذه الوثيقة **لا تفترض** بنية مستودع `lawyer-office2` أو نماذجه أو قاعدة بياناته. قرار الدمج النهائي يبقى بعد فحص ذلك المستودع فعلياً.

## 2. الرؤية المستهدفة

ميزان منصة قانونية سورية تجمع وتفهرس وتسترجع:

- القوانين.
- المراسيم التشريعية.
- الأنظمة والقرارات.
- الاجتهادات والأحكام عند توفر مصادر موثوقة.
- النماذج القانونية.
- البنية الهرمية للتشريع: كتاب، باب، فصل، مبحث، مطلب، مادة.

والمنتج النهائي المستهدف يتكون من:

```text
Flutter
  ├── محادثة قانونية
  ├── مكتبة التشريعات
  ├── البحث النصي والدلالي
  ├── النماذج القانونية
  └── الأجندة والخدمات المساندة

Backend
  ├── API آمن
  ├── قاعدة بيانات قانونية
  ├── محرك بحث نصي ودلالي
  ├── RAG مع الاستشهاد بالمصادر
  └── خدمات إدارة المحتوى والبيانات

Data Platform
  ├── زاحف قابل للاستئناف
  ├── استخراج وتنظيف عربي
  ├── إصدارات الوثائق والمواد
  ├── Embeddings
  └── سجل مصدر وتدقيق كامل
```

## 3. الحالة المؤكدة للمستودع الحالي

### 3.1 ما هو موجود

| المكوّن | الملف | الحالة المؤكدة |
|---|---|---|
| الاستطلاع | `recon.py` | موجود، وفيه تحليل أولي لبنية الموقع والروابط |
| الجلب | `fetcher.py` | موجود، مع Session وتأخير ومحاولات إعادة |
| التنظيف والاستخراج | `extractor.py` | موجود، الإصدار المعلن v3.3 |
| الزحف | `crawler.py` | موجود، الإصدار المعلن v2.1 |
| قاعدة البيانات | `database.py` | SQLite تجريبية مع جداول وثائق ومواد وسجل زحف |
| التصنيف | `extractor.py` و`config.py` | تصنيف heuristic للفروع القانونية |
| اختبار يدوي | `test_extraction.py` | اختبار يعتمد على اتصال خارجي مباشر |

### 3.2 ما لم يثبت وجوده في المستودع

- `requirements.txt` أو `pyproject.toml`.
- `README.md` قبل إضافة هذا التوثيق.
- PostgreSQL أو `pgvector`.
- Embeddings أو Semantic Search.
- FastAPI.
- RAG.
- Flutter.
- قاعدة بيانات أو تصدير بيانات إنتاجي.
- مجموعة Fixtures ثابتة لاختبار الاستخراج.
- CI أو تقرير جودة آلي.
- ملف دستور عمل مشروع ميزان؛ يجب إضافته بعد توفر النسخة الأصلية ومراجعتها.

### 3.3 ملاحظة حول عدد المواد

ورد في وصف المشروع أنه تم استخراج أكثر من 1600 مادة. هذا الرقم لا يمكن التحقق منه من المستودع الحالي وحده، لأن قاعدة البيانات والبيانات التشغيلية غير موجودة ضمن Git. سيتم التعامل معه كرقم يحتاج إلى **تقرير مصدر ومطابقة** عند استلام قاعدة SQLite أو JSON/CSV من البيئة المحلية.

## 4. المبادئ غير القابلة للتفاوض

### 4.1 صحة المصدر والتتبع

كل وثيقة ومادة يجب أن ترتبط بـ:

- رابط المصدر الأصلي.
- وقت الجلب.
- بصمة المحتوى.
- نسخة HTML الخام عند السماح بذلك.
- أداة وإصدار الاستخراج.
- حالة جودة واضحة.

لا يجوز أن ينتج نظام RAG إجابة بلا إمكانية الرجوع إلى الوثيقة والمادة التي استند إليها.

### 4.2 عدم التكرار وقابلية إعادة التشغيل

إعادة تشغيل الزاحف يجب ألا تنشئ نسخاً مكررة من الوثيقة أو المادة. يجب أن تكون عمليات الحفظ idempotent، وأن يكون لكل وثيقة ومادة معرف مستقر لا يعتمد على وقت التشغيل فقط.

### 4.3 الزحف المهذب والمسؤول

- احترام `robots.txt` وسياسة المصدر.
- استخدام User-Agent واضح.
- تطبيق تأخير قابل للضبط بين الطلبات.
- عدم تجاوز حدود المصدر أو تنفيذ زحف عدواني.
- تسجيل حالات المنع والفشل.
- عدم تشغيل زحف واسع قبل اختبار محدود ومراجعة النتائج.

### 4.4 البيانات القانونية ليست بديلاً عن المراجعة القانونية

النص المستخرج مادة أرشيفية للبحث، وليس حكماً بصحة النفاذ أو التعديل أو الإلغاء. لذلك يجب فصل:

- النص الخام.
- النص المنظف.
- نتيجة الاستخراج الآلي.
- حالة المراجعة البشرية.
- معلومات التعديل والإلغاء عند توفرها.

### 4.5 حماية الأسرار والبيانات

- عدم حفظ Tokens أو مفاتيح API في Git أو السجلات.
- استخدام `.env` محلياً مع `.env.example` دون أسرار.
- عدم وضع قواعد البيانات التشغيلية أو HTML الخام الكبير في Git إلا بقرار صريح.
- تنقية السجلات من رؤوس المصادقة والبيانات الحساسة.

### 4.6 الاختبار قبل التوسعة

لا يتم اعتماد تغيير في extractor أو crawler بناءً على تجربة صفحة واحدة. كل تغيير مؤثر يجب أن يملك Fixtures واختبارات تغطي الحالات المتوقعة، مع اختبار شبكة منفصل اختياري.

## 5. البنية المستهدفة

البنية التالية هي اتجاه مستهدف وليست دعوة لنقل الملفات دفعة واحدة:

```text
mizan-law-ai/
├── frontend/                    # تطبيق Flutter
├── backend/
│   ├── app/
│   │   ├── api/                 # FastAPI
│   │   ├── crawlers/            # مصادر ومحرك الزحف
│   │   ├── extraction/          # التنظيف والاستخراج
│   │   ├── nlp/                 # التطبيع والتصنيف
│   │   ├── search/              # البحث النصي والدلالي
│   │   ├── rag/                 # Retrieval + Generation
│   │   ├── database/            # النماذج والوصول للبيانات
│   │   └── services/            # الخدمات المشتركة
│   ├── migrations/              # Alembic أو ما يعادله
│   └── tests/
├── database/                    # إعدادات PostgreSQL/pgvector
├── data/                        # بيانات تشغيلية خارج Git غالباً
├── docs/
├── DELIVERY/
├── pyproject.toml
├── README.md
└── .env.example
```

### قرار الدمج مع `lawyer-office2`

لا يتم اختيار Monorepo أو خدمة مستقلة قبل فحص `lawyer-office2`. الخيارات المقبولة:

1. **دمج منظم داخل Backend ميزان:** نقل وحدات الزاحف إلى `backend/crawlers` مع الحفاظ على حدود واضحة.
2. **خدمة جمع مستقلة:** يبقى الزاحف مشروعاً مستقلاً ويكتب إلى قاعدة مشتركة أو يصدّر عقد بيانات موثقاً.
3. **حل انتقالي:** يبقى المستودع الحالي مستقلاً في المرحلة الأولى، ويُبنى Contract ثابت للدمج لاحقاً.

الافتراضي الآمن إلى حين الفحص هو الخيار الثالث، لأنه يقلل النقل المبكر والمخاطر.

## 6. عقد البيانات المقترح

### 6.1 الوثيقة

```json
{
  "document_key": "sha256:...",
  "title": "قانون ...",
  "document_type": "law",
  "number": 1,
  "year": 2020,
  "branch": "civil_law",
  "branch_confidence": 0.87,
  "source_url": "https://...",
  "source_credibility": 0.6,
  "source_fetched_at": "2026-09-05T00:00:00Z",
  "content_hash": "sha256:...",
  "extraction_version": "4.0.0",
  "review_status": "auto_extracted"
}
```

### 6.2 المادة

```json
{
  "article_key": "sha256:...",
  "document_key": "sha256:...",
  "article_number": "1",
  "article_label": "المادة الأولى",
  "hierarchy_path": [
    "الباب الأول",
    "الفصل الأول"
  ],
  "text": "...",
  "paragraphs": ["..."],
  "char_count": 500,
  "quality_score": 0.94,
  "source_locator": {
    "url": "https://...",
    "html_hash": "sha256:..."
  }
}
```

### 6.3 الكيانات الأساسية في قاعدة البيانات

| الكيان | الغرض |
|---|---|
| `sources` | تعريف المواقع أو الملفات ومصداقيتها وسياسة الزحف |
| `crawl_runs` | تشغيلات الزحف وإحصاءاتها وإصدارات الأدوات |
| `crawl_tasks` | طابور الروابط وحالاتها ومحاولاتها |
| `documents` | الهوية المستقرة للوثيقة |
| `document_versions` | نسخ الوثيقة وتغيراتها عبر الزمن |
| `hierarchy_nodes` | الباب والفصل والمبحث وغيرها |
| `articles` | الهوية المنطقية للمادة |
| `article_versions` | نسخ المادة وتاريخ تغيرها |
| `embeddings` | المتجهات المرتبطة بنسخ المواد أو chunks |
| `precedents` | الاجتهادات والأحكام عند إضافة المصدر المناسب |
| `templates` | النماذج القانونية ومراجعها |

## Phase 1B — Extractor v4

### القدرات المطلوبة

1. تنظيف عربي وUnicode أكثر ثباتاً.
2. إزالة عناصر الصفحة الجانبية والإعلانات والتواقيع.
3. اختيار حاوية المحتوى مع مؤشرات جودة قابلة للتفسير.
4. اكتشاف المواد بالأرقام العربية والهندية وبالصياغات اللفظية.

10. إخراج عقد بيانات ثابت قابل للتخزين والاختبار.

- قانون كامل متعدد المواد.

- مقدمة تسبق المادة الثانية.

- عناصر إعلانية وروابط كثيرة.

- مادة مكررة أو معدلة.

## Phase 1C — زاحف قابل للاستئناف

### التدفق

```text
discover
  → canonicalize URL
  → enqueue task
  → respect robots/rate limit
  → fetch
  → snapshot/hash
  → extract
  → validate quality
  → classify
  → persist idempotently
  → report
```

### العمل

- استبدال الطابور داخل الذاكرة بطابور دائم.
- تطبيع الروابط وإزالة معاملات التتبع فقط عند ثبوت أمان ذلك.
- دعم صفحات الأقسام والتقسيم Pagination.
- معرفات مستقرة للوثائق والمواد.
- إعادة المحاولة حسب نوع الخطأ.
- حفظ حالة المهمة: `queued`, `running`, `success`, `failed`, `blocked`, `needs_review`.
- حفظ HTML الخام اختيارياً خارج Git.
- تطبيق robots.txt فعلياً.
- منع التشغيل المتوازي غير المصرح به على نفس المصدر.
- توفير وضع `dry-run` ووضع عدد محدود من الصفحات.

### معيار الخروج

إيقاف الزاحف ثم تشغيله مجدداً يؤدي إلى استكمال العمل دون تكرار الوثائق أو المواد، مع تقرير قابل للمراجعة.

## Phase 2 — FastAPI وRAG

### FastAPI

- API للوثائق والمواد.
- API للبحث.
- API للمصادر وحالة الزحف للمستخدم الإداري.
- المصادقة والتفويض وفق Backend ميزان.
- Pagination وrate limiting.
- توثيق OpenAPI.

### RAG

- استرجاع chunks موثوقة فقط.
- تمرير مصدر المادة ورقمها إلى طبقة التوليد.
- منع الإجابة عند ضعف الاسترجاع أو التصريح بعدم كفاية المصدر.
- إظهار الاستشهادات في النتيجة.
- تسجيل السؤال والاسترجاع والتقييم دون تخزين أسرار.
- بناء مجموعة تقييم عربية، تشمل الأسئلة التي لا يجوز للنظام أن يخمن إجاباتها.

### معيار الخروج

كل إجابة قانونية تجريبية تعرض مصادرها، وتفشل بشكل آمن عند عدم كفاية البيانات.

## 8. خطة ترحيل البيانات الموجودة

عند توفر قاعدة البيانات المحلية أو تصديرها:

1. أخذ نسخة أصلية لا تُعدل.
2. حساب hash للملف وتسجيل تاريخ الاستلام.
3. فحص schema والأعداد الفعلية.
4. تصدير تقرير:
   - عدد الوثائق.
   - عدد المواد.
   - المواد بلا وثيقة.
   - الوثائق المكررة.
   - المواد القصيرة أو الفارغة.
   - الفروع والتصنيفات.
5. تشغيل Importer على بيئة staging.
6. مقارنة الأعداد والمحتوى.
7. معالجة التكرارات حسب المصدر والبصمة، لا حسب العنوان فقط.
8. اعتماد عملية النقل بعد مراجعة عينة يدوية.
9. الاحتفاظ بنسخة rollback.

## 9. الاختبارات ومقاييس الجودة

### اختبارات الوحدة

- تطبيع الروابط.
- تحويل الأرقام العربية.
- كشف بداية المادة.
- استخراج المادة الأولى.
- استخراج hierarchy.
- التنظيف وإزالة الالتصاق.
- حساب hash.
- التصنيف.

### اختبارات التكامل

- Fetcher مع استجابة ثابتة.
- Extractor مع HTML حقيقي محفوظ.
- حفظ وثيقة وموادها مرة واحدة.
- إعادة الحفظ دون تكرار.
- استئناف Queue.
- migration وimport.

### مؤشرات الجودة

- نسبة الصفحات التي استخرجت بنجاح.
- نسبة الوثائق التي اجتازت legal validation.
- متوسط طول المادة.
- عدد المواد غير المرتبطة بوثيقة.
- معدل التكرار.
- دقة حدود المواد في عينة مراجعة.
- دقة hierarchy في عينة مراجعة.
- زمن الجلب والاستخراج.
- عدد الإخفاقات حسب المصدر.

لا يتم إعلان رقم إجمالي للمواد دون تقرير يذكر طريقة الحساب وتاريخها ومصدرها.

## 10. المخاطر والضوابط

| الخطر | الضابط |
|---|---|

| اعتبار النص المستخرج قانوناً نافذاً | فصل المصدر عن حالة النفاذ والمراجعة البشرية |

## 14. قاعدة التسليم

كل مرحلة تسلّم:

1. كوداً قابلاً للتشغيل.
2. اختبارات أو Fixtures مناسبة.
3. توثيقاً يشرح طريقة التشغيل.
4. تقريراً يذكر ما تم وما لم يتم.
5. Migration أو خطة تراجع عند تغيير البيانات.
6. أمثلة مخرجات يمكن مراجعتها يدوياً.

لا تعتبر عبارة “تم استخراج البيانات” كافية دون مصدر، أعداد، بصمات، وحالة جودة.
