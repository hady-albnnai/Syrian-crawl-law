## 1. البنية الفعلية لمستودع ميزان (`lawyer-office2`)

| البند | الواقع المثبت |
|---|---|
| **النوع** | تطبيق Flutter لسطح مكتب **Windows** — Offline-First V6.2 |
| **Frontend** | Flutter (Dart SDK >=3.10)، بنية `lib/{core,data,presentation}`، 160 ملف Dart، Riverpod + go_router |
| **Backend** | **لا يوجد خادم خلفي إطلاقاً** — لا REST ولا خدمات سحابية |
| **قاعدة البيانات** | Drift/SQLite محلية مشفرة (SQLCipher) مع نظام `schemaVersion` وترحيلات `onUpgrade`، تحرسها اختبارات (`test/schema_migration_test.dart`) |
| **الاستهلاك القانوني** | حزمة ملفات `content/legal_library/laws_decrees/`: فهرس CSV (29 قانوناً) + 12 PDF + 20 مستورد HTML/JSON من `syrian-lawyer.club` (WordPress REST) |
| **عقد الفهرس CSV** | `id,title,type,number,year,date,category,url,format,priority,status,local_path,size_bytes,sha256` |
| **نقطة الاستهلاك في التطبيق** | جدول `LegalLibraryItems` في `schema.dart` (سطر 841): `itemType, title, category, source, sourceUrl, filePath, fileName, extractedText, year, tags, lawNumber, lawKind, lastAmendment, court, chamber...` + جدول `LegalLibraryLinks` |
| **دستور العمل** | `CONSTITUTION.md` — دورة حياة ثلاثية، محظورات تقنية، مبدأ الدقة المتناهية، مبدأ AI-Readiness، هوية بصرية |
| **CI** | بوابة GitHub Actions: `flutter analyze` + `flutter test` + `flutter build windows` |

### ملاحظة تكامل مهمة
مستودع ميزان **يحتوي أصلاً مخرجات شبيهة بعمل زاحف** (مستوردات `syrian-lawyer.club` بصيغة WordPress REST JSON). أي أن التطبيق اعتاد استهلاك «حزم ملفات + فهرس»، وهذا يسهّل الخيار الانتقالي أدناه.

غير قابل للتحقق من المستودع (القاعدة التشغيلية خارجه). يبقى **ادعاءً** حتى تسليم نسخة SQLite أو تصدير JSON/CSV، وعندها يُطبق مسار الترحيل §8 من الخارطة ويصدر تقرير أعداد.

## 3. نقطة التكامل بين المستودعين

```text
Syrian-crawl-law (Python)                     lawyer-office2 (Flutter/Offline)
┌─────────────────────────────┐               ┌──────────────────────────────────┐
│ crawl → extract → SQLite    │               │ content/legal_library/           │
│ documents / articles        │── Exporter ──▶│   laws_decrees_index.csv (فهرس)  │
│ (عقد غني: versions, quality)│   (حزمة ملفات)│   pdf/ + html/ + json/           │
└─────────────────────────────┘               │ → LegalLibraryItems (Drift)      │
                                              └──────────────────────────────────┘
```

**الفجوة:** الزاحف ينتج صفوف SQLite بعقد غني (مواد، هرمية، جودة)، والتطبيق يستهلك ملفات + فهرس CSV بأعمدة ثابتة (تشمل `sha256`). الجسر المطلوب = **مُصدِّر (Exporter)** يولّد حزمة مطابقة لعقد CSV الحالي.

## 4. القرار المعماري (مُوصى به — بانتظار اعتماد المالك)

**الخيار 3 الانتقالي** من الخارطة §5:

- يبقى `Syrian-crawl-law` مستودع Python مستقلاً (الزحف ومعالجة النصوص ثقيلة ولا تنتمي لتطبيق Flutter دون خادم).
- يُبنى Exporter يحوّل المخرجات إلى حزمة `laws_decrees_index.csv` + ملفات، فتدخل ميزان **دون أي تغيير في مخطط Drift**.
- عقد البيانات الغني (documents/articles/versions/embeddings لاحقاً) يبقى أساس PostgreSQL + البحث الدلالي + RAG **إن** قررت المنصة مستقبلاً التحول إلى نموذج خادم.
- **السبب:** ميزان اليوم Offline-First بلا خادم؛ الدمج الفوري في Monorepo أو فرض FastAPI+PostgreSQL الآن = نقل مبكر ومخاطرة بلا حاجة مثبتة.

> ⚠️ توتر معماري يجب أن يحسمه المالك صراحة: الخارطة تستهدف منتجاً خادمياً (FastAPI + PostgreSQL + Flutter متصل)، بينما ميزان القائم تطبيق مكتبي دون اتصال. المساران ليسا متناقضين (الـ Exporter يخدم الأول فوراً ويمهّد للثاني)، لكن **أولوية الاستثمار** قرار مالك لا افتراض.
