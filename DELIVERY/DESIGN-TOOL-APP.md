# تحليل وتصميم: الزاحف كأداة سطح مكتب قابلة للتوزيع

**التاريخ:** 2026-09-05
**الحالة:** تحليل للنقاش — القرارات التقنية النهائية بانتظار اختيار المالك (§9)
**الطلب:** «أريد تصميم زاحف يعمل كأداة — بعد إنهاء تطويره نصدره كتطبيق. بعد التصميم والتطوير يستخرج لي البيانات التي أريدها حتى أصدّرها لتطبيق ميزان.»

---

## 1. تحليل المطلوب

الطلب يحوّل المنتج من «سكربت تطوير» إلى **أداة مستقلة (Product Tool)** لها دورة حياة:

```
تطوير (هذا المستودع) → تغليف (تطبيق Windows) → توزيع → تشغيل لدى المستخدم
   → زحف واستخراج → مراجعة جودة → تصدير حزمة → استيراد في ميزان
```

### الاستنتاجات المترتبة على هذا التحول:
1. **الجمهور لم يعد المبرمج:** الأداة يجب أن تعمل **دون تثبيت Python** ودون طرفية — تطبيق بنوافذ وأزرار.
2. **البيئة المستهدفة Windows** (ميزان نفسه تطبيق Windows لمكتب محاماة) — التغليف يجب أن يُبنى على Windows.
3. **سلامة البيانات تصبح مسؤولية الواجهة:** حدود الزحف، robots، والتأكيد قبل التصدير — كلها قرارات مستخدم، فالواجهة يجب أن تجعل الخيار الآمن هو الافتراضي.
4. **الجودة قبل التصدير:** المستخدم يجب أن **يرى** ما سيصدَّره (مواد مستخرجة، درجات جودة، عناصر تحتاج مراجعة) — لا تصدير أعمى.
5. **قابلية التوزيع تعني إصدارات:** كل حزمة تصدير تحمل إصدار الأداة وإصدار الاستخراج (موجود أصلاً في عقد البيانات: `extraction_version`).

## 2. المعمارية: «نواة + قشرة» (Core + Shell)

القاعدة التصميمية الأهم: **المنطق لا يعرف الواجهة**. النواة مكتبة Python نقية قابلة للاختبار headless، والقشرة غلاف رقيق يستدعيها. هذا يحمي الاستثمار: تتغير الواجهة أو تُضاف CLI موازية دون لمس المنطق، وتبقى اختبارات pytest (الموجودة) سارية على النواة.

```text
mizan-harvester/                      ← اسم مقترح: «حاصدة ميزان»
├── core/                             # النواة — بلا أي UI، تُختبر بـ pytest
│   ├── config.py                     # الإعدادات + .env
│   ├── sources/                      # محوّلات المصادر (منتدى phpBB الآن، غيره لاحقاً)
│   ├── crawl_queue.py                # طابور دائم قابل للاستئناف (تسليم 3)
│   ├── fetcher.py                    # جلب مهذب + robots فعلي (منجز P0)
│   ├── extractor.py                  # استخراج v4 (تسليم 2)
│   ├── storage.py                    # SQLite: documents/articles/crawl_runs
│   ├── quality.py                    # legal_score + قواعد needs_review
│   └── exporter.py                   # ★ مولّد حزمة ميزان (العقد أدناه §5)
├── app/                              # القشرة — نوافذ تقدم شاشات §4
│   └── ui_*
├── cli.py                            # واجهة طرفية موازية (اختبار/أتمتة/CI)
├── packaging/                        # ملف spec PyInstaller + أيقونة + Inno Setup
└── tests/                            # اختبارات النواة (بلا شبكة)
```

> **حالة التنفيذ 2026-09-05:** العقد منفَّذ — `app/core_data.py` هو الواجهة الحقيقية (استبدل `app/mock_data.py` بنفس الأسماء والأشكال)، والشاشات تعرض من القاعدة نفسها: طابور/سجل/وثائق/بوابة تحقق محسوبة من الملفات. انظر ملحق «ربط الواجهة بالنواة» في PLAN-CHECKLIST.

**لماذا مصدر بيانات واحد (SQLite) للواجهة والتصدير؟** الواجهة تعرض من القاعدة نفسها التي يقرأ منها المصدِّر — فلا يمكن أن يرى المستخدم شيئاً ويصدَّر شيء آخر (مبدأ «لا رقم بلا تقرير»).

## 3. دورة الاستخدام (User Journey)

```
[1] تحديد النطاق        المستخدم يختار المصدر/الأقسام/عدد الصفحات — ووضع «تجريبي» افتراضي
        ↓
[2] الزحف                شريط تقدم + إحصاء حي (صفحات/وثائق/مواد/فشل) + إيقاف واستئناف
        ↓
[3] المراجعة             جدول الوثائق: العنوان، الفرع، عدد المواد، درجة الجودة،
        ↓                حالة المراجعة — فلترة «تحتاج مراجعة» — معاينة نص المادة
[4] التصدير لميزان       اختيار الوثائق (أو الكل المجتاز) → توليد الحزمة → تقرير تحقق
        ↓
[5] التسليم              مجلد الحزمة يُنسخ إلى ميزان (يدوياً الآن، وبمستورد CSV لاحقاً)
```

## 4. شاشات الأداة (5 شاشات فقط — لا أكثر)

| # | الشاشة | المحتوى | القرار الذي تتخذه |
|---|--------|---------|-------------------|
| 0 | **استكشاف المصادر** | بحث عن مصادر جديدة (3 قنوات)، جدول مرشحين بدرجات وأحكام، اعتماد/استبعاد | «من يُزحف؟» |
| 1 | **النطاق** | المصادر **المعتمدة فقط**، الأقسام، حد الصفحات، وضع تجريبي/محدود/كامل | «ماذا أجمع؟» |
| 2 | **التشغيل** | تقدم حي، سجل أحداث، إيقاف/استئناف (الطابور الدائم) | «متى أتوقف؟» |
| 3 | **المكتبة** | جدول وثائق + مواد، درجة جودة، معاينة | «هل الناتج صالح؟» |
| 4 | **التصدير** | تحديد المجتاز، توليد الحزمة، تقرير التحقق | «ماذا أسلّم لميزان؟» |
| 5 | **الإعدادات** | تأخير، robots (مفعّل دائماً وغير قابل للتعطيل في وضع الإنتاج)، مجلد البيانات، User-Agent | «كيف تتصرف الأداة؟» |

### قناة استكشاف المصادر (نُفذت نواتها 2026-09-05: `discovery.py` + اختبارات + شاشة 0)

```
بحث (DDG بلا مفتاح / Bing بمفتاح .env) ─
إدراج يدوي                              ├─→ تقييم موحّد ─→ sources(proposed) ─→ موافقة صريحة ─→ نطاق الزحف
دليل بذور مرفق (SEED_SOURCES)           ─┘   (جلب مهذب ← استخراج ← legal_score ← كشف محرك)
```

قواعد نافذة: المرشح `proposed` ولا يدخل الزحف قبل `approved`؛ التقييم يجلب
عبر fetcher (فيحترم robots تلقائياً)؛ الحكم يُسجل بأسبابه؛ السجل idempotent
بمفتاح sha256 للرابط المطبَّع. واقع مُثبت: DDG بلا مفتاح قد يصدّ بتحدي روبوت
(HTTP 202 من بيئة الفحص) — لذلك المسار الموثوق للتوزيع الواسع هو Bing بمفتاح
أو دليل البذور، ويُعالَ الصدّ صراحة برسالة واضحة لا بابتلاع الخطأ.

مبدأ واجهة: **الخيار الآمن هو الافتراضي** — robots مفعل، وضع محدود افتراضياً، تصدير المجتاز فقط افتراضياً.

## 5. عقد «حزمة ميزان» (Mizan Export Package) — قلب التصميم

الحزمة مجلد واحد قابل للنقل، مبني على عقد ميزان المثبت في ADR-001 (أعمدة `laws_decrees_index.csv` الحالية حرفياً):

```text
mizan_package_2026-09-05/
├── laws_decrees_index.csv     # الأعمدة الحالية حرفياً:
│                              # id,title,type,number,year,date,category,url,
│                              # format,priority,status,local_path,size_bytes,sha256
├── files/
│   ├── civil_code_1949.md     # نصوص مستخرجة — أسماء ملفات لاتينية آمنة (ASCII slug)
│   ├── civil_code_1949.html   # (اختياري) الصفحة الأصلية للتدقيق
│   └── ...
├── articles/                  # (اختياري للتوافق المستقبلي) مواد مفصلة JSON
│   └── civil_code_1949.json   # عقد المادة من ROADMAP §6.2 (article_key, hierarchy…)
├── manifest.json              # هوية الحزمة: إصدار الأداة، إصدار الاستخراج، تاريخ
│                              # التشغيل، مصدر البيانات، أعداد موثقة، بصمات
└── REPORT.md                  # تقرير إنساني: ماذا/متى/كم/ما الذي فشل ولماذا
```

### قواعد التحقق قبل اعتماد الحزمة (بوابة التصدير):
- كل صف في CSV يقابله ملف موجود فعلاً، و`sha256` و`size_bytes` مطابقان.
- لا `id` مكرر، ولا عنوان فارغ، ولا `local_path` بمسار مطلق.
- الوثائق ذات `quality_score` دون الحد أو `review_status = needs_review` **لا تُصدَّر افتراضياً** (قابلة للتضمين بقرار صريح مع وسمها في REPORT).
- الحزمة **read-only منطقياً**: التوليد في مجلد جديد دائماً — لا كتابة فوق حزمة سابقة.

### لماذا أسماء ملفات ASCII والعناوين عربية في CSV؟
الفهرس الحالي لميزان يستخدم أسماء ملفات عربية (تعمل)، لكن الأسماء المولدة آلياً بالعربية عبر منصات وأدوات ضغط مختلفة عرضة لتشوهات ترميز. القاعدة: **العنوان العربي في CSV، واسم الملف slug لاتيني** — وهو نمط موجود أصلاً في ميزان (`civil_code_1949`).

### ما يلزم في ميزان لاحقاً (موثق في ADR-001، لا يُنفذ هنا):
مستورد CSV حقيقي بدل القائمة المحشورة، يقبل `format = md/html/txt` إضافة إلى `pdf`.

## 6. مقارنة تقنيات التغليف والواجهة

### أ) تغليف التطبيق (لا Python على جهاز المستخدم)

| التقنية | المزايا | العيوب | الحكم |
|---------|---------|--------|-------|
| **PyInstaller (مجلد) + مثبّت Inno Setup** | ناضج ومجرّب، مجلد واحد أو مثبّت، يدعم العربية | حجم 40–80MB، تنبيهات AV عرضية (أقل بكثير من نمط one-file) | ★ **الموصى به** |
| PyInstaller one-file | ملف واحد | إقلاع بطيء (فك ضغط مؤقت)، إنذارات AV أكثر | للاستعراض لا للتوزيع |
| Nuitka | إقلاع أسرع، حجم أصغر | بناء أعقد وسلاسل أدوات أطول | بديل لاحق إن لزم |
| MSI/MSIX | توزيع مؤسساتي | تعقيد توقيع وشهادات | غير مطلوب الآن |

ملاحظة بناء: PyInstaller **لا يبني عبر المنصات** — يُبنى التطبيق على Windows (يدوياً أو عبر GitHub Actions `windows-latest`، وهو نمط موجود أصلاً في CI ميزان).

### ب) إطار الواجهة

| الإطار | المزايا | العيوب | لمن يناسب |
|--------|---------|--------|------------|
| **PySide6 (Qt)** | جداول واحترافية قصوى، ناضج، فرز/فلترة جاهزة | حجم أكبر (~60–100MB مثبّت) | أداة بيانات جدّية ★ **الموصى به** |
| pywebview + HTML/CSS | جمال كامل بهوية ميزان (كحلي+ذهبي)، حجم صغير | يحتاج WebView2 (موجود في Win10/11 الحديثة)، جدولة الجداول يدوية | لو الأولوية جمالية بحتة |
| CustomTkinter | أخف وأبسط | جداول ضعيفة، مظهر محدود | نموذج أولي سريع |
| Flet (Flutter) | تناغم تقني مع ميزان | نضج التغليف المكتبي أقل مجازفةً منه في PySide6 | مغامرة غير محسوبة الآن |

**التوصية:** PySide6 للجدية والجداول + PyInstaller/Inno. (القرار للمالك — §9).

## 7. الأثر على خارطة الطريق (إعادة ترتيب الأولويات)

طلب «الأداة» + قرار ADR-001 (RAG محلي في ميزان لا خادم) يعيدان رسم المسار الحرج. المراحل الخادمة (PostgreSQL/pgvector/FastAPI) تبقى مؤجلة اختيارية، ويصير المسار الحرج:

```
تسليم 1: أساس التطوير (pyproject, logging, CLI, fixtures, CI)      ← التالي مباشرة
تسليم 2: Extractor v4 (جودة الاستخراج — مدخلات الأداة)
تسليم 3: زحف قابل للاستئناف (الطابور الدائم — prerequisite لشاشة التشغيل)
تسليم 4′: تثبيت نموذج SQLite النهائي (بديل مسار PostgreSQL المؤجل)
تسليم 8: Exporter — حزمة ميزان + بوابة التحقق (§5)
تسليم 9: قشرة PySide6 + تغليف PyInstaller/Inno + أول إصدار موقّع v1.0
——— مسار اختياري لاحق (إن قرر المالك) ———
تسليم 5/6: embeddings وبحث دلالي — يُعاد توجيههما لخدمة RAG ميزان المحلي
```

**مبدأ الاعتماد:** لا تُبنى الواجهة قبل استقرار النواة (تسليمات 1–3)، لأن كل تغيير في النواة بعد التغليف يكلف إعادة بناء وتوزيع. الواجهة تُبنى مرة واحدة على عقد نواة ثابت.

## 8. المخاطر والضوابط

| الخطر | الضابط |
|-------|--------|
| إنذارات مضاد الفيروسات ضد exe غير موقّع | نمط المجلد+المثبّت، توثيق إرشاد المستخدم، توقيع Code-Signing لاحقاً (اختياري مدفوع) |
| تشوه العربية في أسماء الملفات/السجلات | slug لاتيني للملفات، UTF-8 للسجلات، الواجهة نفسها لا تعتمد console |
| زحف طويل ينقطع | الطابور الدائم (تسليم 3) شرط قبل شاشة التشغيل |
| تصدير بيانات رديئة لميزان | بوابة §5: المجتاز فقط افتراضياً + REPORT |
| إصدار قديم لدى المستخدم يصدّر بصيغة منسوخة قديمة | manifest.json يحمل إصدار الأداة والاستخراج؛ ميزان مستقبلاً يرفض الحزم الأقدم من حد أدنى |
| اختلاف بنية المصدر (منتدى يتغير) | محوّلات مصادر معزولة + fixtures + تنبيه انخفاض الجودة |
| المستخدم يظن النص المستخرج قانوناً نافذاً | REPORT.md يحمل إخلاء مسؤولية ثابتاً + `review_status` ظاهر في شاشة المراجعة |
